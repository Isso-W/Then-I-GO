# 那我走 (Then-I-GO) — 项目说明书

> "用户说「那我走」，系统来决定去哪。"

## 一、产品定位

**那我走** 是一款 AI 驱动的周末散步推荐 App。用户不需要做任何攻略，只需要告诉系统今天的心情和时间，AI 就会生成一条个性化的探索路线，带着用户一站一站地走、打卡、领优惠券、发现隐藏任务，最后自动生成一条 Vlog 回忆。

核心理念：**把「去哪玩」的决策成本降到零。**

---

## 二、多 Agent 协作架构

系统不是一个大模型包办一切，而是把路线生成流程拆成多个协作模块——3 个真正的 AI Agent（调 LLM、有推理-行动循环或上下文决策能力）+ 2 个确定性辅助模块（纯规则计算，零 LLM 调用）：

### AI Agent（调用 Gemini，具备推理与行动能力）

| Agent | 职责 | 输入 → 输出 |
|---|---|---|
| **路线 Agent** (routeAgent) | 编排路线 + 写故事 | 候选 POI + 偏好 → 站点序列 + 任务文案 + 奖励 |
| **审查 Agent** (routeReviewer) | 质检路线合理性 | 路线 + 地理数据 → 通过 / 调序 / 重选 |
| **对话 Agent** (chatAgent) | 探索中实时改路线 | 用户消息 + 当前路线 → 回复 + 路线操作指令 |

路线 Agent 和审查 Agent 构成 **ReAct 循环**（Reason + Act）：路线生成后交给审查 Agent 做"品控"，检查品类是否重复（连续两个奶茶店？）、节奏是否合理（吃完火锅紧接着去健身？）、时间是否可行（1 小时安排了 5 站？）。不通过就带着审查意见反馈给路线 Agent 重新生成，最多修正一轮。类似于工厂里的 QC 环节——AI 给 AI 做质检。

对话 Agent 在探索过程中持续感知用户意图 + 当前路线上下文，输出自然语言回复的同时附带路线操作指令（替换/跳过/加站），具备改变系统状态的行动能力。

### 确定性辅助模块（纯规则计算，不调 LLM）

| 模块 | 职责 | 说明 |
|---|---|---|
| **用户画像** | 收集 MBTI + 兴趣标签 | 冷启动 onboarding 收集，存 localStorage，路线生成时作为 prompt 上下文注入。不是独立 agent，是数据透传 |
| **POI 评分过滤** (poiFilter) | 12 维评分 + 候选排序 | 确定性评分函数，按偏好/天气/时间/距离等 12 个维度打分，输出 top 15 候选给路线 Agent |

### Vlog 生成（当前为单次 LLM 调用，未来升级为 Agent）

| 模块 | 职责 | 输入 → 输出 |
|---|---|---|
| **Vlog 生成** (vlogAgent) | 生成探索回忆视频脚本 | 路线站点 + 风格 → 分镜脚本 + 旁白 + 配乐 |

当前实现是一次 Gemini 文本补全——输入站点列表和风格，输出分镜脚本 JSON。原本设计为完整的 Vlog Agent（调用 image-to-video 模型生成真实视频片段、多轮迭代优化剪辑节奏），但 **image-to-video 的 per-user × per-second 成本在 demo 环境下不可承受**，因此降级为文本生成 + 前端程序化动画（地图回放 + Live2D 呼吸）的方案。完整的 Vlog Agent 能力列入后续工作。

## 三、12 维 POI 智能评分

不是简单地按评分排序，而是用 12 个维度综合打分，让"对的人在对的时间遇到对的店"：

| 维度 | 逻辑 | 举例 |
|---|---|---|
| **基础分** | 评分越高越好 (rating 3.0→0, 4.5→0.75) | 4.8 分的万圣书园排在前面 |
| **标签亲和** | 用户选的兴趣 × POI 标签的语义相似度矩阵 | 选了「文艺」→ 书店、美术馆加分 |
| **心情匹配** | POI 是否适合当前心情 | 「想放松」→ 清吧、公园加分 |
| **天气适配** | 实时天气 → 室内/室外偏好 | 下雨天 → 室外 POI 扣分，室内加分 |
| **时段合理** | 当前几点 × 活动类型的时间曲线 | 上午推书店，晚上推酒吧 |
| **等位惩罚** | 排队时间占总时长的比例 | 1 小时行程推排队 40 分钟的海底捞不合理 |
| **停留合理** | 单站停留不能占总时长一半以上 | 1 小时行程不会推 KTV (120min) |
| **新鲜度** | 去过的地方降权，没去过的加分 | 上次去过的咖啡厅这次排后面 |
| **价格匹配** | 配合「省钱」偏好 | 选了省钱 → price_level=1 的加分翻倍 |
| **人流偏好** | 同行人 × 拥挤度 | 情侣 → 人少的清吧；朋友 → 热闹的烧烤 |
| **口味匹配** | 餐饮类 POI × 用户口味偏好 | 选了「麻辣」→ 火锅、川菜加分 |
| **距离惩罚** | 离出发点越远扣分越多（按时长缩放） | 1 小时行程更倾向近的 POI |

**小巧思：距离惩罚会随时长自适应。** 同样 1km 的距离，在 1 小时行程里扣分很重（走过去就要 12 分钟），在整天行程里几乎不扣分。公式：`-(距离km × 1.5 / (总分钟数 / 30))`。

**小巧思：品类上限保证多样性。** 即使评分前 10 全是咖啡厅，每个品类最多选 2 个进候选池（半天/整天行程的餐饮类放宽到 3 个，因为要安排饭点）。

## 四、200 个真实感 POI 数据库

不接入任何第三方 API（高德收费、美团不开放、Google 国内受限），而是用 Gemini 生成 + 人工逐条审查，commit 进仓库实现完全离线运行。

**数据规模**：200 个 POI，31 个品类，覆盖北京五道口 2.5km × 2.8km 的区域。

**每个 POI 包含 15 个字段**：名称、品类、偏好标签、地址、坐标、营业时间、平均停留时间、排队时间、拥挤度、价格档位(1-4)、评分、一句话评价、3 条用户评论、心情匹配、MBTI 标签、最佳时段。

**品类分布**（按数量）：
- 餐饮类（75 个）：咖啡厅 20、奶茶甜品 13、日韩料理 12、北京风味 10、通用餐厅 9、素食轻食 6、夜宵烧烤 6、火锅 5、小吃 5、东北菜 4、美食城 3、美食街 2
- 文化类（43 个）：文创小店 12、书店 9、景点/地标 9、公园绿地 7、美术馆 5、花店 5
- 娱乐类（36 个）：酒吧 5、酒吧清吧 5、livehouse 5、运动娱乐 6、桌游/密室 5、KTV 3、夜店 3、电影院 3、台球/棋牌 3、电竞/网咖 3
- 生活类（23 个）：共享空间/自习室 6、宠物友好咖啡 6、健身/瑜伽 5

**小巧思：所有 POI 都落在路上。** 生成坐标后统一用 `snapPOIsToRoads` 脚本吸附到路网——按路段长度加权随机采样，保证坐标在路面上而非楼里或绿地中间。这样导航寻路时 Dijkstra 一定能找到路径，用户不会被导到"地图上没有路的地方"。

**小巧思：标签是人工审查的，不是模板分配。** 星巴克不标 `art`（它是连锁不是文艺小店）、健身房不标 `outdoor`（它是室内）、Manner Coffee 标 `budget` 而不是 `art`（它的卖点是便宜不是氛围）。34 个标签错误被逐条修正。

**小巧思：评论内容扎根五道口。** 不是泛泛的"环境好服务棒"，而是"从清华骑车过来专门吃他家饺子"、"深夜从图书馆出来最想来的地方"——每条评论都带有五道口高校区的生活质感。

## 五、真实路网 + Dijkstra 导航

### 路网

34 条路段、28.2km 总路长，覆盖五道口核心区所有主干道和支路。11 块地表多边形（5 校园 / 3 公园 / 1 水体 / 2 商业区）渲染在地图底层做视觉参考。

### 导航

- **Dijkstra 最短路**：从用户当前位置到目标站点，沿真实路网寻路，渲染紫色虚线 + 方向箭头。
- **方向面板**：旋转箭头图标实时指向目标 + 距离 + 预计到达时间，不用文字方向（"向东走 200 米"在手机上没有意义，用户不知道东是哪边）。
- **Heading 追踪**：追踪用户行走方向（移动 >2m 才更新），箭头角度 = 行走方向到目标的相对夹角。

**小巧思：双端点选路避免回头。** 用户当前位置先 snap 到最近路段的两个端点，分别算到目标的总距离，选更短的那个作为起点。这解决了一个微妙的 bug：如果用户在路段中间，默认总是从同一端出发会导致导航线从身后绕一圈。

## 六、探索体验设计

### 偏好收集（5 步快速配置）

1. **心情**：开心 / 疲惫 / 无聊 / 想放松 / 想探索 / 想吃好的（6 选 1）
2. **时长**：1 小时 / 2 小时 / 半天 / 整天（4 选 1）
3. **兴趣标签**：文艺 / 户外 / 美食 / 热闹 / 拍照 / 小众 / 省钱（可多选）
4. **同行人**：独自 / 情侣 / 朋友 / 亲子（4 选 1）
5. **安排程度**：别让我思考 / 正常探索（2 档）

### 安排程度的差异化

| 功能 | 别让我思考 | 正常探索 |
|---|---|---|
| 下一站信息 | 隐藏名字和奖励（到达才揭晓） | 全部显示 |
| A/B 岔路选择 | 无（系统直选） | 有（两个气质相反的候选） |
| 新鲜度权重 | 强避重（去过的 -0.8） | 弱避重（去过的 -0.4） |

**小巧思：「别让我思考」是默认模式。** 产品洞察——大多数用户说"那我走"的时候，就是不想做任何决定。所以默认帮他们选好一切，想要掌控感的用户主动切到"正常探索"。

### 动态站点数量

站点数量不是固定的，而是根据时长自动调整：

| 时长 | 主线站点 | 隐藏任务 | 合计 |
|---|---|---|---|
| 1 小时 | 1 站 | 1 个 | 2 |
| 2 小时 | 1 站 | 1 个 | 2 |
| 半天 | 2 站 | 1 个 | 3 |
| 整天 | 3 站 | 1 个 | 4 |

### 隐藏任务

不是另外生成的——Gemini 一次调用多生成 1 个站点，最后一个 `pop()` 出来作为隐藏任务。这保证隐藏任务的坐标真实、品类不与主线冲突、故事文案风格一致。

**小巧思：隐藏任务的位置连续性。** 完成隐藏任务后推进到下一步时，avatar 的位置设为隐藏任务坐标而非清空——否则用户会看到小人从隐藏任务位置瞬移回主线上一站，体验很割裂。

**小巧思：隐藏任务可跳过 + RLHF 全链路响应。** 隐藏任务弹窗提供"跳过，直接结算"选项——用户不是必须接受每一个惊喜。跳过后系统基于行为信号（`hiddenTriggered`）在全链路做出响应：故事页素材集不显示该站点、Vlog 配图列表移除该站、历史记录中隐藏任务条目消失、结算奖励不计入。这是一个典型的 **RLHF（Human Behavior Response Feedback）** 模式——用户的行为（跳过）即反馈，系统无需额外询问就能做出一致性调整，而不是跳过了还到处看到"你错过了一个隐藏任务"。

### A/B 岔路抉择

第一站打卡后弹出两个**气质相反**的候选第二站（比如"安静的独立书店 vs 热闹的精酿酒吧"），附一句抉择提示文案。二选一后直接替换 waypoints[1]，下游逻辑无需任何改动。

### 探索中聊天改路线

右下角紫色气泡 → 打开对话面板，用自然语言跟 AI 聊天。AI 可以执行 4 种路线操作：

- `replace_next`：替换下一站（"我不想去书店了，有没有有意思的？"）
- `skip_current`：跳过当前站（"这个排队太长了，跳过"）
- `add_stop`：末尾加站（"走完了还有时间，再推荐一个？"）
- `none`：纯聊天（"这家店有什么推荐的菜？"）

**小巧思：候选 POI 来自真实数据。** 聊天 Agent 的 prompt 里注入了当前路线附近未使用的 8 个候选 POI，AI 只能从里面选——不会编造不存在的店。

### 天气感知装备确认

路线生成后（不是之前），根据实时天气和路线中的 POI 品类动态生成装备清单：
- 下雨 → 提示带雨伞
- 路线包含需要身份证的景点 → 提示带身份证
- 默认不勾选，用户自己确认带了哪些

### 接近打卡（模拟 LBS）

打卡按钮不拦截（路上随时可拍照记录），但走到目标 30m 内时顶部亮绿色提示"到了·可打卡"——给到达感，但不强制必须到了才能操作。

## 七、奖励系统

### 优惠券

每站打卡奖励一张与品类相关的优惠券（如咖啡厅 → ¥15 饮品抵扣券，书店 → ¥20 购书折扣券）。格式统一为"¥金额 + 券名"，不发徽章、不发 XP——只发真正有价值的东西。

**小巧思：品类→奖励映射表锚定 Gemini 输出。** 不是让 AI 自由发挥写奖励（会出现"恭喜获得探索勋章"这种空洞文案），而是在 prompt 里给每个候选 POI 附上推荐奖励（含具体金额），Gemini 可以微调文案但锚点在那里。

### 优惠券使用

背包页点击优惠券 → 弹出仿真 QR 二维码弹窗（可模拟核销）。

### 成就徽章

8 枚成就徽章（连续打卡 / 隐藏任务 / 集齐品类 / 集券数量等），基于真实 `tripHistory` 计算而非硬编码：
- 连续打卡天数从实际日期序列计算
- 品类通关从 visited waypoints 的 emoji 多样性计算

## 八、Vlog 自动生成

### 设计思路：拆解"视频"为各自便宜的部分

不调视频生成模型（per-user × per-second 的成本 demo 扛不住），而是把"视频"拆成免费/廉价的组件：

| 组件 | 来源 | 成本 |
|---|---|---|
| 镜头清单 / 分镜表 | 路线 waypoints 直接当分镜 | 免费 |
| 沿街路径几何 | Dijkstra 寻路 + 折线插值 | 免费（复用路网） |
| 旁白 / 字幕 / 标题 / BGM / 金句 | 一次 Gemini 文本补全 | ~0.001 美元 |
| 画面运动 | 地图回放（小人沿街走）+ Live2D 呼吸动画 | 0 token（纯前端） |

### 三种风格

赛博朋克 / 复古胶片 / 日系清新，影响旁白语气、BGM 推荐、画面纹理层（扫描线+霓虹 / 胶片噪点+暖色暗角 / 漏光效果）。

### 回放体验

1. **地图回放阶段**：小人沿路网逐段走，轨迹按风格色生长，到站时站点标记"砰"地弹出。顶部 IG Stories 风格分段进度条。
2. **到站特写**：用户照片的 Live2D 呼吸动画（微缩放 + 微摇晃 + 微旋转，幅度极小看不到边缘） + 字幕旁白 + 风格纹理叠层。
3. **战报卡**：风格标签 + 标题 + AI 金句 + 路线缩略图 + 数据格子（里程/打卡点/奖励）+ 分享文案。

**小巧思：回放镜头跟随。** 回放时 SVG viewBox 以 avatar 为中心、500m 半径裁剪，镜头跟着小人走。战报卡的缩略图用同一个组件但切换为 `frozen` 模式（静态全貌）。

**小巧思：到站回调走 ref 而非 state。** `onStopChange` 回调如果放在 useEffect 依赖里，父组件切照片触发重渲染会把动画 effect 重启。改用 ref 存回调，动画循环内读 ref.current——渲染归渲染，动画归动画，互不干扰。

## 九、历史记录 + 自学习闭环

### 行为信号采集

探索完成后持久化 `TripRecord`，包含：
- 每站是否实际到访（visited）
- A/B 岔路选了哪个
- 聊天改路线的操作日志
- 是否触发了隐藏任务
- 探索总时长和距离
- 用户反馈（emoji 一键评价）

### 极轻反馈设计

探索结束后弹出"跟我吐槽一下"浮层，一行 emoji（6 个表情），点一个就完成。5 秒不操作自动消失。历史页面还可以给每个站点单独打 emoji 评价。

**小巧思：反馈门槛要低到不存在。** 如果让用户写文字评价，99% 的人会跳过。一行 emoji 点一个不到 1 秒，获取率远高于任何文字或星级评价。

### 足迹地图

个人页面展示去过的所有站点，用 SVG mask 实现迷雾效果——去过的点挖洞透出底图，未探索区域被迷雾覆盖。探索越多，地图越清晰。

## 十、主题系统

支持深色/浅色主题。首次进入按系统时间自动选择（6:00-18:00 日间，其余夜间），手动切换后持久化。全局通过 CSS 变量 + `data-theme` 属性切换，包括 Vlog 回放的地图配色、路网颜色、地表色块都会跟随主题变化。

## 十一、技术亮点总结

| 亮点 | 说明 |
|---|---|
| **纯前端，无后端** | 所有 AI 调用通过 Vite 开发插件代理到 Vertex AI / AI Studio，生产环境零服务器 |
| **ReAct 审查循环** | AI 生成 → AI 审查 → 带反馈重生成，保证路线质量不靠运气 |
| **确定性时间预检** | 审查 Agent 调 Gemini 前先算步行+停留时间，超预算 50% 直接打回，省一次 API 调用 |
| **12 维评分系统** | 不是"评分高就推"，而是 mood × weather × time × distance × novelty 多维权衡 |
| **200 POI 人工审查** | Gemini 生成 + 逐条 tag/mood/price 校验，不是 demo 数据随便糊 |
| **路网 Dijkstra + snap** | 所有 POI 吸附到路面，寻路有路可走，不穿墙不飞线 |
| **Vlog 零视频模型** | 拆解为文本补全 + 前端程序化动画，成本趋近于零 |
| **探索中自然语言改路线** | 聊天 Agent 只从真实 POI 池里选，不会编造不存在的店 |
| **RLHF 行为响应反馈** | 用户跳过隐藏任务 → 故事/Vlog/历史/奖励全链路同步移除，行为即反馈，无需额外询问 |
| **全链路可观测日志** | 打开 DevTools Console 即可追踪完整 AI 决策过程：POI 评分排名（`console.table`）、prompt 原文与 Gemini 原始返回（折叠分组）、ReAct 审查结果、营业时间预检、隐藏任务分配、聊天改路线候选过滤——每个阶段用 emoji 前缀区分（📋/📤/📥/🔄/✅/🚪/🎯/💬），Demo 演示时可实时展示 AI 不是黑箱 |
| **行为信号闭环** | 去过/跳过/停留/反馈全部采集，为偏好自学习预埋数据通路 |

## 十二、项目规模

- 测试：4 个测试文件，78 个 vitest 用例
- Gemini 模型：`gemini-2.5-flash-lite`（稳定性优先）
- 前端框架：React + Tailwind CSS v4 + motion/react
